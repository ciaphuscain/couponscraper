# Benchmarks and experiments

**Environment:** Linux x86_64 VM, 4 vCPU, Python 3.13.17, SQLite 3.45.1, 2026-10-26 (re-run after the
Telegram, observation, inference, advice and reminder features were added). Raw output:
`benchmarks/results/bench-vm.json`, `benchmarks/results/experiments.json`. Reproduce with
`python -m benchmarks.bench` and `python -m benchmarks.experiments`. All data is synthetic and
generated by those scripts. Your Windows laptop will differ: re-run there before quoting numbers.

product), 2 cards in wallet, 60 price observations per product.

### Optimisations that were measured to help
| Change | Before | After |
|---|---|---|
| Per-kind pruning (3) + 2,000-combination cap per instrument | 60 offers: 3.5 s | ~0.1 s |
| Four bounding readings instead of 2ⁿ for unknown bases | evaluate (stress): ~115 ms | ~58 ms |
| Version-keyed evaluation cache | warm watchlist (100, stress): ~10 s | ~5 ms |
| Purge stale-version cache entries + keep top-50 scenarios | soak peak traced memory 14.9 MB | 1.0 MB |

**First bottleneck:** cold per-product evaluation, linear in watched products and in sitewide
offers. Next step if it matters: recompute only products whose inputs changed.

### Long-running soak (Experiment G, 31 simulated days)
3,000 cycles × 15 simulated minutes: 20 watched products, a 100-record source re-ingested each
cycle, price updates for 5 products and a full alert run every cycle.

| Check | Result |
|---|---|
| Offer rows vs distinct fingerprints | 80 / 80 (no duplicates) |
| Duplicate alert dedup keys | 0 |
| Notifications sent | 8 in 31 days (out of 8,692 alert rows; the rest suppressed or deduplicated; the nightly job prunes suppressed rows after 14 days, which this harness doesn't run) |
| Traced Python memory | 979 KB → 1,305 KB over 3,000 cycles, growth flattening (+14 KB over the last 300 cycles); peak 2.8 MB |

The residual growth was traced (tracemalloc snapshot diff) to cached evaluations holding objects
derived from each product's growing price history. It scales with stored data and is bounded by
the cache size (≤ 512 products), and isn't a per-cycle leak. Earlier 600-cycle run: 598 → 741 KB.
A real-time 30-day run on the laptop is still worth doing; this is simulated time on one machine.

## Experiments

### B — Offer-text parsing accuracy
Dataset: 26 author-written strings (19 offers, 7 non-offers) modelled on amazon.in phrasing.
**Not held-out**: the first run exposed a real bug (Amazon Pay UPI cashback classified as bank
cashback) and one wrong label, both fixed. So the final score shows the parser handles these
phrasings. It is **not** an estimate of real-world accuracy.

| Metric | First run | Final |
|---|---|---|
| Exact field match | 17/19 | 19/19 |
| Non-offers accepted (false positives) | 0/7 | 0/7 |
| Offers rejected as unknown | 0/19 | 0/19 |

Decision: keep deterministic parsing; measure the unknown rate on your real captures (Health →
source runs "rejected") before considering an LLM.

### C — Ranking strategies (2,000 random synthetic cases)
| Strategy | Picks a different scenario than risk-adjusted | Mean expected regret | Regret if cashback settles 25% less than assumed |
|---|---|---|---|
| Highest advertised discount | 10.2% | ₹14.03 | ₹15.60 |
| Lowest checkout price | 19.1% | ₹90.52 | ₹87.80 |
| Lowest effective price if all cashback pays | 10.2% | ₹14.03 | ₹15.60 |
| Risk-adjusted (default) | — | ₹0 | ₹0.39 |

Caveat: regret is computed under the optimizer's own probability model, so risk-adjusted is
optimal *by construction*. The useful findings are *how often* naive rankings diverge (10–19% of
cases) and that ignoring deferred cashback entirely (lowest checkout) is the costliest naive
rule. Under a 25% settlement shortfall, risk-adjusted still loses only ₹0.39 on average.

### D — Deal-quality alerts (400 synthetic 90-day price series)
Classes: genuine drop (12–20% below steady), inflated reference price, pre-sale inflation
(raised 25% for two weeks, then "discounted" back), steady noise (±3%).

| Rule | Alerts | False positives | Precision | Recall |
|---|---|---|---|---|
| Naive (≥20% off list, or ≥10% day-over-day) | 370 | 270 | 0.27 | 1.00 |
| History-aware (first version) | 128 | 28 | 0.78 | 1.00 |
| History-aware (final: must clear max(5%, 2×volatility) below median) | 100 | 0 | 1.00 | 1.00 |

Same caveat: the final rule was revised after seeing these synthetic series, and real price
behaviour is messier. The robust finding is the large gap between list-price rules and
history-based rules.

### F — Source failure
Source X (coupon) goes down after 1 hour; source Y (bank offer) keeps working; 7 simulated days.

* X is retried with exponential backoff (7 fetch attempts in 7 days) and **auto-disabled after 5
  consecutive failures** (~hour 12).
* X's coupon stays in the confirmed answer for its 48 h freshness window, then turns STALE and
  drops out. The answer falls back to Y's offer (₹9,300 → ₹9,600). The offer is never "kept alive"
  by the outage.
* Alerts: 1 (the original). The run exposed a downgrade alert ("₹400 off" after the ₹700 offer
  went stale), which is now suppressed for 7 days.
